## Verdichtete Bewertung entlang der Achsen

### 🧠 Komplexität

- Polling und Cursor-Management sind bewusst einfach gehalten (reine ISO-Timestamps, kein komplexer State).
- Tab-Logik kapselt die komplette Interaktion in einer Funktion, nutzt semantische Datenattribute und Delegation – gut lesbar und lehrbar.

### 🧩 Wartbarkeit

- Benennungen (z. B. `initTeachingLivePolling`, `updateLiveStatusTimestamp`) sind selbsterklärend.
- ENV-basierte Konstante `TEACHING_LIVE_POLL_INTERVAL_SECONDS` macht Konfiguration nachvollziehbar.
- Tests adressieren SSR-Verhalten und Konfigurierbarkeit des Polling-Intervalls; JS-Verhalten selbst ist noch nicht separat getestet.

### 🛡️ Robustheit

- Polling startet nur, wenn `#live-status`, `#live-section` und ein Cursor vorhanden sind.
- Delta-Handler geht defensiv mit JSON um (prüft `dict`, filtert `cells` sorgfältig, normalisiert `changed_at`).
- Fehlerpfad: `updateLiveStatusForError` integriert Live-Status in die HTMX-Fehlerbehandlung.

### 🔐 Sicherheit

- CSP:
  - Inline-Skript im SSR-Detail-Partial entfernt; Tabs werden aus `gustav.js` initialisiert.
  - Notification-Styles sind aus Inline-JS nach CSS gewandert.
- Auth/RLS:
  - Kein Eingriff in API-/RLS-Pfade; Teaching-Live bleibt auf Teacher im Kurs beschränkt.
- PII:
  - Polling-Cursor basiert nur auf Zeitstempeln, keine zusätzlichen personenbezogenen Daten im Frontend.

### 📘 Dokumentation

- Ticket- und Plan-Dateien beschreiben:
  - User Stories und BDD-Szenarien (Auto-Polling, Tabs, CSP-Fix).
  - Root Cause (CSP blockiert Inline-Skript) und gezielte Gegenmaßnahmen.
- Dieses Dokument fasst Review-Perspektive (Nutzen/Risiko) für zukünftige Refactors zusammen.

### ⚙️ Konsistenz

- OpenAPI / DB-Schema:
  - Unverändert; alle Änderungen liegen in SSR-/JS-/CSS-Schicht.
- Frontend-Pattern:
  - Verwendung von HTMX-Attributen (`hx-get`, `hx-trigger`, `hx-swap`) folgt bestehenden Konventionen.
  - Neue CSS-Klassen für Notifications fügen sich in die existierende Utility-/Component-Struktur ein.

## Review-Findings (priorisiert)

### MUST FIX (kritisch)

- Keine sicherheits- oder API-kritischen Punkte identifiziert.

### SHOULD FIX (wichtig)

1. **JS-Tests für Tabs/Polling ergänzen (Achse: TEST/Wartbarkeit)**
   - Problem: Tab-Verhalten und Cursor-Updates sind nur indirekt über SSR-Tests abgesichert.
   - Risiko: Regressions im Browser (z. B. nach Refactor in `gustav.js`) würden erst spät auffallen.
   - Vorschlag:
     - DOM-/Integrationstests für `initTeachingLiveTabs` und `initTeachingLivePolling` ergänzen (z. B. Headless-Browser oder Playwright).
     - Mindestens einen Test, der das `liveCursorUpdated`-Event simuliert und überprüft, ob `data-updated-since` und der sichtbare Zeitstempel aktualisiert werden.

2. **Delta-Handler-Fehlerpfad klarer dokumentieren (Achsen: ROBUSTHEIT/DOKUMENTATION)**
   - Problem: Das defensive Verhalten bei unerwarteten JSON-Strukturen (z. B. keine `cells`) ist im Code nachvollziehbar, aber nicht explizit kommentiert.
   - Vorschlag:
     - Kurzen Docstring/Kommentar am `teaching_unit_live_matrix_delta_partial` ergänzen:
       - Warum bei ungültigen/unerwarteten Daten ein leerer 204/200-Body zurückgegeben wird.
       - Wie der `HX-Trigger`-Header die Cursor-Logik trennt.

3. **Konfiguration der Polling-Intervalle sichtbarer machen (Achsen: KONSISTENZ/DOKUMENTATION)**
   - Problem: `TEACHING_LIVE_POLL_INTERVAL_SECONDS` ist aktuell nur im Code ersichtlich.
   - Vorschlag:
     - Kurzen Abschnitt in den Ops-/Env-Dokumenten ergänzen (z. B. `docs/ARCHITECTURE.md` oder ein Env-Reference-Dokument), der `GUSTAV_TEACHING_LIVE_POLL_INTERVAL_SECONDS` erklärt (Default, empfohlene Werte, Auswirkungen).

4. **Testabhängigkeit vom Default-Intervall explizit machen (Achse: TEST/KONSISTENZ)**
   - Problem: `test_live_page_includes_status_cursor_and_polling_attributes` erwartet aktuell hart `hx-trigger="every 3s"`.
   - Risiko: Wenn das Env-Default geändert wird, kann der Test „zufällig“ abweichen, ohne dass klar ist, ob Code oder Konfiguration schuld sind.
   - Vorschlag:
     - Im Test knapp dokumentieren, dass er bewusst den Default (3s) prüft, oder die Erwartung aus der bekannten Default-Konstante ableiten, damit der Zusammenhang für Lernende transparent ist.

### NICE TO HAVE (optional)

1. **Helper für Timestamp-Normalisierung extrahieren (Achse: KOMPLEXITÄT/WARTBARKEIT)**
   - Idee: Die Logik zum Parsen/Normalisieren von ISO-Timestamps in eine kleine Hilfsfunktion auslagern, um Lesbarkeit und Wiederverwendbarkeit zu erhöhen.

2. **Fehlertexte für Live-Status zentralisieren (Achse: KONSISTENZ/UX)**
   - Idee: Die deutschsprachigen Statusmeldungen („Live-Ansicht: Verbindung unterbrochen.“ etc.) in Konstanten bündeln, um Übersetzungen/Anpassungen zu vereinfachen.

3. **„Keine Aufgaben“-Fall und Polling im Plan kurz erläutern (Achse: KONSISTENZ/ROBUSTHEIT)**
   - Beobachtung: Aktuell wird auch dann Polling konfiguriert, wenn die Lerneinheit keine Aufgaben hat.
   - Einordnung:
     - Technisch unkritisch (Delta liefert schlicht keine Änderungen), aber leicht vom ursprünglichen BDD-Szenario abweichend („kein Polling ohne Zellen“).
   - Vorschlag:
     - Im Auto-Polling-Plan oder hier kurz vermerken, dass dieses Verhalten bewusst akzeptiert wird (geringe Last, einfachere Implementierung), damit zukünftige Leser den Trade-off verstehen.
