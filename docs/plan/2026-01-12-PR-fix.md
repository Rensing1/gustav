## Problem‑Detail (MUST FIX): Upload‑Intents fail‑open

### Warum ist das kritisch?
Upload‑Intents geben einen **signed capability** aus (presigned URL + Key). Wenn das ohne verifizierte Membership/Visibility passiert, kann ein Angreifer:
- Storage‑Kosten verursachen / Bucket zumüllen (DoS/Abuse), selbst wenn er später keine Submission finalisieren darf.
- “Security posture” verwässern: Autorisierung hängt von Verfügbarkeit einzelner Komponenten ab.

### Root Cause (aktuell)
Im Upload‑Intent‑Handler gibt es einen `except Exception:`‑Fallback, der bei Repo/DB‑Problemen am Ende **permissiv** werden kann (“keep behavior permissive …”), statt fail‑closed zu antworten.

### Zielverhalten (Design)
- Wenn Membership/Visibility nicht zuverlässig geprüft werden kann: **503 Service Unavailable** (fail‑closed).
- Wenn der Student nicht berechtigt ist: **404 Not Found** (fail‑closed, leak‑minimizing; wie aktuell beabsichtigt).
- Spec‑Konsistenz: 503 darf nicht nur “Storage unavailable” bedeuten, sondern auch “authorization check unavailable” (oder eigener error/detail Code).

### Konkretes Zielverhalten (HTTP‑Contract, präzise)
Für `POST /api/learning/courses/{course_id}/tasks/{task_id}/upload-intents`:

- **200 OK (happy path)**
  - Headers: `Cache-Control: private, no-store`, `Vary: Origin`
  - Body: `StudentUploadIntentResponse` (inkl. `intent_id`, `storage_key`, `url`, `headers`, `accepted_mime_types`, `max_size_bytes`, `expires_at`)
- **403 Forbidden (CSRF)**
  - Headers: `Cache-Control: private, no-store`, `Vary: Origin`
  - Body (Error): `{"error":"forbidden","detail":"csrf_violation"}`
- **404 Not Found (fail‑closed, not allowed / not released)**
  - Headers: `Cache-Control: private, no-store`, `Vary: Origin`
  - Body (Error): `{"error":"not_found"}` (optional `detail`)
- **503 Service Unavailable (fail‑closed, authorization check unavailable)**
  - Headers: `Cache-Control: private, no-store`, `Vary: Origin`
  - Body (Error): `{"error":"service_unavailable","detail":"authorization_unavailable"}`
  - Wichtig: **keine** Exception‑Details (keine PII, keine Interna).

## Ops‑Hinweis: Supabase Migration‑History Drift (Prod‑Risiko)
Symptom:
- `supabase migration up` bricht ab mit “Remote migration versions not found in local migrations directory.”

Einordnung:
- Das ist ein **History‑Mismatch** zwischen DB (`supabase_migrations.schema_migrations`) und deinem Git‑Ordner `supabase/migrations/`.
- Wenn wir das nicht sauber halten, ist ein späteres Prod‑Update riskant (unklare Reihenfolge, fehlende Files, Repair‑Workarounds).

Regel (Team‑Hygiene):
- Migrationen **immer** via `supabase migration new` erstellen und **sofort** committen.
- Bereits “applied” Migrationen **nie** umbenennen.
- Bei Drift zuerst: `git pull` (Migrationsfiles fehlen lokal) oder `supabase db pull` (lokal ↔ remote abgleichen).
- `supabase migration repair ...` nur nutzen, wenn der Status in der DB wirklich falsch ist (z. B. echtes Revert‑Szenario) — sonst verschleiert es die Ursache.
