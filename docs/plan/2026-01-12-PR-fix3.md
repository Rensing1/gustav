**Ziel:** Spec und Implementierung stimmen überein, ohne Privacy‑Leaks.

- Given H5P storage ist bereit When `GET /h5p/healthz` Then `200` und JSON enthält

- Given H5P storage ist nicht bereit When `GET /h5p/healthz` Then `503` und JSON
  enthält `storage.ok=false` und enthält **kein** `root`/`error`.

Umsetzung:
1) **Contract‑First:** `api/openapi.yml` aktualisieren
   - `H5PStorageReadiness`: nur `ok` (und ggf. `additionalProperties: false`)
   - `/h5p/healthz` Description: keine internen Pfade (z.B. kein `/data/h5p`)
   - `/h5p/healthz` responses bleiben `200/503` wie dokumentiert.
2) **RED:** Neuer pytest‑Test, der Spec‑Schema für `/h5p/healthz` validiert
   - Empfohlen: `backend/tests/test_openapi_h5p_healthz_contract.py`
   - Assert: `H5PHealth.storage` hat nur Property `ok`, kein `root`/`error`.
3) **GREEN:** (voraussichtlich) keine Code‑Änderung am Sidecar nötig
   - Falls doch: Sidecar Healthz Payload strikt minimal halten.
4) **Verifikation lokal:**
   - `.venv/bin/pytest -q backend/tests/test_openapi_h5p_healthz_contract.py`
   - `.venv/bin/pytest -q backend/tests/test_h5p_healthz_privacy_contract.py`

Done‑Definition:

- Privacy‑Contract bleibt grün (kein Pfad/keine Errors im öffentlichen Healthz).
