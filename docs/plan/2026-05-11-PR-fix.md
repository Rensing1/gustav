## Kurzfazit

Die CLI ist in Scope, Tests und Dokumentation erstaunlich weit. Kritisch ist aber die Auth-Grenze: CLI-Tokens werden runtime breiter akzeptiert als vertraglich geplant. Dadurch können CLI-Tokens aktuell Token-Management-Endpunkte erreichen. Das muss vor PR-Freigabe behoben werden.

## MUST-FIX

- [SEC] CLI-Tokens können Token-Management-Endpunkte erreichen — `backend/web/main.py:421@9e07bca`, `backend/web/routes/app.py:1087@9e07bca` — Impact: Ein CLI-Token mit `write` kann `POST /api/app/profile/cli-tokens` nutzen und neue Tokens mit stärkeren Scopes erzeugen, obwohl Plan und Doku das ausschließen. — Fix: Akzeptiere CLI-Bearer nur für explizit erlaubte Teaching-Authoring-Pfade oder lehne Profil-/Token-Endpunkte bei `request.state.cli_token_id` hart ab.
- [SEC] DB-Token-Store fällt in Nicht-Test-Umgebungen still auf Memory zurück — `backend/web/main.py:300@9e07bca` — Impact: In Prod/Compose können Tokens pro Prozess volatil werden; Restart/Multi-Worker bricht Nutzbarkeit und verschleiert Konfigurationsfehler. — Fix: Schlage bei `CLI_TOKENS_BACKEND=db` fail-fast fehl statt auf Memory zurückzufallen; erlaube Memory nur explizit per Konfiguration.

## Reparaturplan – 2026-05-11 20:21

### 1. CLI-Token-Reichweite begrenzen

- Finding: `[SEC] CLI-Tokens können Token-Management-Endpunkte erreichen`.
- Warum offen: `backend/web/main.py` akzeptiert `gustav_cli_...` aktuell in der allgemeinen Bearer-Auth, bevor der Zielpfad eingegrenzt wird.
- Regeln/Kontext: Security first, API Contract-First, `identity_access` verantwortet AuthN/AuthZ; Teaching-Endpunkte behalten ihre fachlichen Authoring-Guards.
- Dateien: `api/openapi.yml`, `backend/web/main.py`, `backend/tests/test_auth_middleware.py`, `backend/tests/test_openapi_profile_contract.py`.
- Contract-first: Profil-Token-Endpunkte dokumentieren explizit, dass CLI-Bearer dort nicht akzeptiert wird.
- Test-first: Regressionstests für CLI-Bearer auf `/api/app/profile/cli-tokens` und `/api/teaching/views/teacher-home`; positiver Gegencheck für `/api/teaching/units`.
- Minimaler Fix: CLI-Bearer nur für `/api/teaching/units` und `/api/teaching/units/...` zulassen.
- Akzeptanz: CLI-Authoring funktioniert weiter; CLI-Tokens können keine weiteren Tokens erstellen/widerrufen.

### 2. DB-Token-Store fail-fast machen

- Finding: `[SEC] DB-Token-Store fällt in Nicht-Test-Umgebungen still auf Memory zurück`.
- Warum offen: `backend/web/main.py` fängt `DBCLITokenStore`-Initialisierungsfehler ab und nutzt `InMemoryCLITokenStore`.
- Regeln/Kontext: Lokal = Prod; Konfigurationsfehler dürfen nicht als flüchtiger Runtime-Modus versteckt werden. Owner: `identity_access` plus Platform/App-Konfiguration.
- Dateien: `backend/web/main.py`, `backend/tests/test_cli_tokens.py` oder ein kleiner Auth-Wiring-Test, `.env.example`, `docs/references/gustav_cli.md`.
- Contract/Migration: Keine OpenAPI- oder Schemaänderung.
- Test-first: Store-Wiring-Test, der im DB-Modus einen Initialisierungsfehler erwartet statt Memory-Fallback.
- Minimaler Fix: Helper für CLI-Token-Store-Auswahl; DB-Modus propagiert Fehler, Memory-Modus bleibt explizit möglich.
- Akzeptanz: Prod-nahe Konfiguration startet nicht mit unpersistierten CLI-Tokens.

### 3. CLI-Fehlerparser robust machen

- Finding: `[BUG] CLI crasht bei nicht-JSON API-Fehlern`.
- Warum offen: `_http_json` ruft `json.loads` für Erfolg und `HTTPError` ohne Fallback auf.
- Regeln/Kontext: KISS, FOSS/lernbarer Code, keine Token-Leaks in Fehlermeldungen.
- Dateien: `backend/tools/gustav_cli/cli.py`, `backend/tests/test_gustav_cli.py`.
- Contract/Migration: Keine.
- Test-first: Nicht-JSON `HTTPError` und nicht-JSON Erfolgsantwort liefern strukturierte, tokenfreie Fehler statt Traceback.
- Minimaler Fix: kleine JSON-Fallback-Funktion mit kurzer Textvorschau.
- Akzeptanz: CLI zeigt verständliche `API-Fehler (...)`-Meldung und leakt keine Tokens.

### 4. Unit-Delete-DSN im Compose-Pfad absichern

- Finding: `[BUG] units delete scheitert im lokalen Compose-Smoke-Test mit storage_adapter_unavailable`.
- Warum offen: Der Storage-Metadaten-Cleanup nutzt einen DSN aus dem Repo bzw. Service-Fallback; Compose stellt noch keinen expliziten containerfähigen `SERVICE_ROLE_DSN` bereit.
- Regeln/Kontext: Lokal = Prod, Compose-Service-Namen statt `127.0.0.1` im Container. Owner: `teaching` und Platform/App-Konfiguration.
- Dateien: `docker-compose.yml`, `docs/references/config_matrix.md`, bestehende Teaching-Delete-Tests.
- Contract/Migration: Keine.
- Test-first: Config-Test, der `SERVICE_ROLE_DSN` im Webservice mit `supabase_db_gustav-alpha2:5432` erwartet.
- Minimaler Fix: `SERVICE_ROLE_DSN` im Webservice setzen; Dokumentation aktualisieren.
- Akzeptanz: Unit-Delete kann im Container denselben DB-Service erreichen wie die Teaching-Repository-DSN.
